# Архитектура

Целевой поток, **ещё не реализованный целиком**:

```text
Flutter / локальная SQLite
  → FastAPI: запрос ограничений и бюджета
  → DeepSeek: предложение меню только из каталога
  → серверная проверка: ограничения, порции, КБЖУ, целые упаковки и бюджет
  → результат на Flutter → локальная SQLite
```

Небольшой серверный проект без микросервисов и аккаунтов. Клиент хранит
настройки, меню и заметки; сервер — каталог и будущие временные задания.
Результат модели не является доверенным расчётом и не должен отправляться
клиенту как проверенный без независимой проверки сервера.

## Текущая реализация

`create_app()` собирает FastAPI и тонкие маршруты. В lifespan читается локальный
JSON-каталог и проверяется Pydantic v2. Ошибки чтения, формата, полей и повторные
ID прерывают запуск с понятным сообщением, без содержимого файла в ошибке.
Каталог хранится в памяти процесса. Путь по умолчанию и относительный путь
из настройки разрешаются от корня проекта, не cwd; абсолютный путь поддерживается.
`/health` проверяет работающий процесс, не БД/DeepSeek. Каталог валидируется
до начала обслуживания любых запросов. Удаление файла после startup не меняет
загруженный каталог. Для обновления нужен перезапуск.

Отдельные `api/`, `core/`, `schemas/`, `services/`. `calculate_menu()` не зависит
от FastAPI: проверяет ссылки и считает КБЖУ, потребность и покупки целых упаковок.
`POST /v1/menu-calculations` использует уже загруженный каталог; цены и КБЖУ
от клиента не принимаются. Оптимизатора нет; расчет не вызывает DeepSeek.
Настройки через pydantic-settings, ключ — SecretStr. Модель DeepSeek настраивается
отдельно, не наследуется от модели OpenCode. API запускается без ключа и модели.
JSON-каталог — только демонстрация, не источник проверенных цен и нутриентов.

## Генерация MEAL-2: только сервис и ручной CLI

```text
JSON-файл → GenerationRequest + серверный каталог
  → MenuGenerationService → DeepSeekProvider (HTTPX /chat/completions, JSON Output)
  → GeneratedPlan → явное преобразование в MenuCalculationRequest с исходным бюджетом
  → calculate_menu(round_output=False) → проверка ограничений
  → при нарушениях до двух исправлений с полной перепроверкой
  → GenerationResult с округленным расчетом, предупреждениями и метаданными
```

`GeneratedRecipe` расширяет `Recipe` шагами и заявленным временем; старый расчетный
HTTP-контракт не изменен. Вычисления не дублируются: то же ядро возвращает
неокругленные КБЖУ для проверки включительных диапазонов. Внешний расчетный API
по-прежнему округляет вывод. Допуск задает серверная продуктовая настройка
`GENERATION_NUTRITION_TOLERANCE` (по умолчанию ±10% каждого показателя каждого дня).
Бюджет, исключения и допуск никогда не ослабляются автоматически. Нелюбимые ID
дают мягкое предупреждение; неизвестные ID анкеты отвергаются до сетевого вызова.

Владелец HTTP-клиента — вызывающая сторона: CLI создает один `DeepSeekProvider`
в `async with` на весь цикл, переиспользует и закрывает его также при ошибках.
Подмена `httpx.AsyncBaseTransport` позволяет полностью автономные тесты.
Сейчас в lifespan API нет клиента DeepSeek: нет публичного endpoint и не нужны
неиспользуемые ресурсы. При добавлении заданий общими ресурсами будет владеть lifespan.

Правила системы, данные пользователя и отфильтрованный серверный каталог —
отдельные сообщения. JSON Schema и пример задают форму, но ответ всегда считается
недоверенным. Модель получает только каталог и поля анкеты, без ключа и внутренних
ID пользователя. Сырые ошибки, полные анкеты, меню, Authorization и reasoning_content
не логируются и не возвращаются в диагностике. Промпт не заменяет серверную проверку.

Технические ограничения: 3 вызова, max_tokens, четыре HTTP timeout, общий deadline,
потоковое чтение тела до byte-limit перед JSON-разбором, лимиты схемы и обратного
контекста исправления (100 нарушений, предыдущий план до 64 KiB). История исправлений
не накапливается. Обрабатывается ровно один JSON-объект, без извлечения из текста;
пустой/обрезанный ответ и дубли ключей не считаются успехом. Transport retries=0,
redirect и прокси из окружения отключены. Ошибки сети/HTTP заканчивают цикл сразу.
Timeout не означает отсутствия расходов: запрос уже мог попасть к провайдеру.

`python -m meal_budget.generate_menu` читает анкету до 64 KiB, каталог и настройки,
ключ только из окружения (не `.env`); сохраняет только полностью проверенный результат
атомарно без перезаписи по умолчанию только внутри игнорируемого `generated/`.
`--output` — относительный путь; абсолютные пути, `..` и symlink запрещены.
Обход каталогов и публикация через dir_fd/O_NOFOLLOW не следуют symlink;
временные файлы также остаются в generated/. Сохраняются demo-маркировка, предупреждения,
допуск, число вызовов, длительность и фактические модель/usage при наличии.
Проверка не доказывает реальное время приготовления, безопасность или медицинскую
полноценность меню. Аккаунтов, БД, очередей и оптимизатора нет.

Ключ до HTTPX проверяется на печатный ASCII без управляющих символов и очищается
от внешних ASCII-пробелов: это устраняет утечку через DEBUG-ошибку h11, не выключая логи.
`Accept-Encoding: identity`, отказ от других Content-Encoding до чтения тела
и `aiter_raw()` исключают неограниченную распаковку до byte-limit.
Регрессия заголовка проходит настоящий AsyncHTTPTransport/httpcore/h11 с
подмененным network backend, без сокетов; остальные сетевые сценарии — MockTransport.

## Точность денег

Чтение чисел JSON через `parse_float=Decimal`, внутренние суммы и умножения
только Decimal. Валюта — рубль; не хранить деньги в binary float.
В денежном JSON-сериализаторе Decimal преобразуется в число, максимум два
значимых десятичных разряда и предел 1 000 000 рублей позволяют проверить
обратное чтение в Decimal. Это преобразование транспортного формата,
не финансовая арифметика. Расчет использует локальный Decimal-контекст с
точностью 80 значащих цифр и ROUND_HALF_UP только для вывода до двух знаков.
Общий целый знаменатель порций сохраняется при агрегации КБЖУ и потребности:
периодические дроби не меняют границы округления и число упаковок.

## Будущая БД и миграции

PostgreSQL пока не требуется, подключений нет. Хранилище будет выбрано при
реализации временных заданий. Если используется PostgreSQL, деньги —
`NUMERIC(..., 2)`, не FLOAT. Миграции серверной схемы — **yoyo-migrations**,
не Alembic: версии, явные связи/порядок, корректный rollback где возможен,
документированные команды apply/rollback, credentials через окружение.
Применение к чистой тестовой БД и доступный rollback проверяются тестами.
Миграции запускаются отдельно от API. Сейчас нет зависимости yoyo и фиктивных
миграций. Миграции локальной SQLite во Flutter не относятся к серверному yoyo.
