# Архитектура

Целевой поток, **ещё не реализованный целиком**:

```text
Flutter / локальная SQLite
  → FastAPI: запрос ограничений и бюджета
  → DeepSeek: предложение меню только из каталога
  → серверная проверка: ограничения, порции, КБЖУ, целые упаковки и бюджет
  → результат на Flutter → локальная SQLite
```

Небольшой серверный проект без микросервисов и аккаунтов. Клиент хранит
настройки, меню и заметки; сервер — каталог, установки MEAL-9 и временные задания.
Результат модели не является доверенным расчётом и не должен отправляться
клиенту как проверенный без независимой проверки сервера.

## Текущая реализация

Корневой `main.py` содержит настоящую сборку приложения: `create_app()`, lifespan,
подключение маршрутов, middleware и обработчиков ошибок, владение ресурсами.
`manage.py` запускает Uvicorn с factory=True, loopback/8000 по умолчанию и workers=1.
Пакет `meal_budget/` находится в корне рядом с main.py/manage.py. Адаптера и второго
main.py нет, код запуска не модифицирует sys.path. Внутренние импорты фабрики —
`from main import create_app`; запускаемый объект — `main:create_app --factory`.
Каталог и настройки по-прежнему разрешаются от корня проекта, не cwd;
зависимости остаются в Python 3.13 / .venv из uv.lock. Docker запускает корневой manage.py.
Настройки фабрики загружаются при ее вызове, `manage.py --help` их не требует.
Reload допускается только при выключенной HTTP-генерации; proxy_headers и access_log
локального launcher выключены. Новых заданий при старте нет; при включенной
HTTP-генерации ранее принятые queued восстанавливаются по правилам MEAL-8.

`create_app()` собирает FastAPI и тонкие маршруты. В lifespan читается локальный
JSON-каталог и проверяется Pydantic v2. Ошибки чтения, формата, полей и повторные
ID прерывают запуск с понятным сообщением, без содержимого файла в ошибке.
Каталог хранится в памяти процесса. Путь по умолчанию и относительный путь
из настройки разрешаются от корня проекта, не cwd; абсолютный путь поддерживается.
`/health` проверяет работающий процесс, не БД/DeepSeek. Каталог валидируется
до начала обслуживания любых запросов. Удаление файла после startup не меняет
загруженный каталог. Для обновления нужен перезапуск.

Отдельные `api/`, `core/`, `schemas/`, `services/`. `calculate_menu()` не зависит
от FastAPI: проверяет ссылки и считает КБЖУ, потребность и покупки целых упаковок.
`POST /v1/menu-calculations` использует уже загруженный каталог; цены и КБЖУ
от клиента не принимаются. Оптимизатора нет; расчет не вызывает DeepSeek.
Настройки через pydantic-settings, ключ — SecretStr. Модель DeepSeek настраивается
отдельно, не наследуется от модели OpenCode. По умолчанию API запускается без ключа и модели.
JSON-каталог версионирован и содержит происхождение конкретных товаров.
Сбор MEAL-4 был заблокирован HTTP 403; в MEAL-5 импортированы 70 наблюдаемых SKU,
версия `5ka-2026-10-14-observed-v3`, включая кешированные представления карточек.
Цены, география и наличие не подтверждены; сохранен статус `demo_unverified`.
По умолчанию выбран явно синтетический demo-каталог data/products.json;
отдельные fixtures — для тестов.
Реальный снимок выбирается через CATALOG_PATH=data/5ka-products.json, без fallback.
Пустой выбранный каталог допустим
при startup; генерация возвращает catalog_unavailable до проверки/вызова провайдера.

## Генерация MEAL-2: только сервис и ручной CLI

```text
JSON-файл → GenerationRequest + серверный каталог
  → MenuGenerationService → DeepSeekProvider (HTTPX /chat/completions, JSON Output)
  → GeneratedPlan → явное преобразование в MenuCalculationRequest с исходным бюджетом
  → calculate_menu(round_output=False) → проверка ограничений
  → при нарушениях до двух исправлений с полной перепроверкой
  → GenerationResult с округленным расчетом, предупреждениями и метаданными
```

`GeneratedRecipe` расширяет `Recipe` шагами и заявленным временем;
расчетная логика сохранена. MEAL-4 добавляет версию в ответ и унифицирует
числовую сериализацию. Вычисления не дублируются: то же ядро возвращает
неокругленные КБЖУ для проверки включительных диапазонов. Внешний расчетный API
по-прежнему округляет вывод. Допуск задает серверная продуктовая настройка
`GENERATION_NUTRITION_TOLERANCE` (по умолчанию ±10% каждого показателя каждого дня).
Бюджет, исключения и допуск никогда не ослабляются автоматически. Нелюбимые ID
дают мягкое предупреждение; неизвестные ID анкеты отвергаются до сетевого вызова.

Владелец HTTP-клиента — вызывающая сторона: CLI создает один `DeepSeekProvider`
в `async with` на весь цикл, переиспользует и закрывает его также при ошибках.
Подмена `httpx.AsyncBaseTransport` позволяет полностью автономные тесты.
При выключенном HTTP endpoint lifespan API не создает клиент DeepSeek.
При включенном MEAL-3 lifespan владеет одним DeepSeekProvider/HTTPX-клиентом
и MenuGenerationService на все запросы и закрывает клиент при shutdown.

Правила системы, данные пользователя и отфильтрованный серверный каталог —
отдельные сообщения. JSON Schema и пример задают форму, но ответ всегда считается
недоверенным. Модель получает только каталог и поля анкеты, без ключа и внутренних
ID пользователя. Сырые ошибки, полные анкеты, меню, Authorization и reasoning_content
не логируются и не возвращаются в диагностике. Промпт не заменяет серверную проверку.

MEAL-6 использует отдельный `PromptProduct` с id/name/state/state_basis,
nutrition_per_100g/package_size_g/price. Все разрешенные SKU остаются в компактном
JSON; provenance и legacy-поля не удаляются из исходного каталога/API/ядра.
Общие ограничения цен, географии/условий и as_sold — однократный catalog_context.
Полная JSON Schema и правила ответа сохранены; размеры — в [EVALUATION](EVALUATION.md).

Технические ограничения: 3 вызова, max_tokens, четыре HTTP timeout, общий deadline,
потоковое чтение тела до byte-limit перед JSON-разбором, лимиты схемы и обратного
контекста исправления (100 нарушений, предыдущий план до 64 KiB). История исправлений
не накапливается. Обрабатывается ровно один JSON-объект, без извлечения из текста;
пустой/обрезанный ответ и дубли ключей не считаются успехом. Transport retries=0,
redirect и прокси из окружения отключены. Ошибки сети/HTTP заканчивают цикл сразу.
Timeout не означает отсутствия расходов: запрос уже мог попасть к провайдеру.

`python -m meal_budget.generate_menu` читает анкету до 64 KiB, каталог и настройки,
ключ только из окружения (не `.env`); сохраняет только полностью проверенный результат
атомарно без перезаписи по умолчанию только внутри игнорируемого `generated/`.
`--output` — относительный путь; абсолютные пути, `..` и symlink запрещены.
Обход каталогов и публикация через dir_fd/O_NOFOLLOW не следуют symlink;
временные файлы также остаются в generated/. Сохраняются demo-маркировка, предупреждения,
допуск, число вызовов, длительность и фактические модель/usage при наличии.
Проверка не доказывает реальное время приготовления, безопасность или медицинскую
полноценность меню. CLI не использует БД/очередь; аккаунтов и оптимизатора нет.

Ключ до HTTPX проверяется на печатный ASCII без управляющих символов и очищается
от внешних ASCII-пробелов: это устраняет утечку через DEBUG-ошибку h11, не выключая логи.
`Accept-Encoding: identity`, отказ от других Content-Encoding до чтения тела
и `aiter_raw()` исключают неограниченную распаковку до byte-limit.
Регрессия заголовка проходит настоящий AsyncHTTPTransport/httpcore/h11 с
подмененным network backend, без сокетов; остальные сетевые сценарии — MockTransport.

## Закрытый HTTP-сценарий MEAL-3

```text
POST /v1/menu-generations
  → GenerationGuard: Bearer / compare_digest → свободный слот → тело до 64 KiB
  → FastAPI / GenerationRequest → прежний MenuGenerationService и расчетное ядро
  → полностью проверенный GenerationResult или безопасная типизированная ошибка
```

Маршрут и middleware подключаются только при `GENERATION_HTTP_ENABLED=true`.
Непустой `GENERATION_ACCESS_TOKEN` — отдельный SecretStr, не ключ DeepSeek;
неправильная конфигурация access token отвергается в create_app без значения секрета.
HTTPBearer в OpenAPI описывает контракт, фактическая проверка в чистом ASGI middleware
происходит раньше JSON-парсера и provider. Входное тело буферизуется с пределом
65536 байт; проверка Content-Length не заменяет проверку фактических чанков.

Эффективный путь guard и обоих обработчиков ошибок определяется через
`starlette._utils.get_route_path(scope)` — ту же функцию использует маршрутизация
FastAPI/Starlette. Она снимает только полный `root_path` на границе `/`, один раз,
не делает replace и учитывает накопленный префикс вложенных mounts. Uvicorn с
`--root-path /api` добавляет `/api` к ASGI path; сравнение с полным path было дефектом P1.
Это внутренний API: текущие Starlette 1.7.0 / FastAPI 0.143.0 закреплены в uv.lock;
обновление версий требует повторных тестов границ префикса, mounts и живого Uvicorn.
Собственная копия алгоритма не используется, чтобы не разойтись с router.

После проверки токена, захвата слота и ограниченного чтения тела guard создает
в scope приватное подтверждение, значением которого служит **тот же объект scope**.
Endpoint проверяет идентичность объекта; HTTPBearer сам по себе недостаточен.
Отсутствие подтверждения, bool или подтверждение от другого scope дают безопасный
401 без provider. Клиент не может записывать ASGI scope из headers/JSON; в finally
подтверждение удаляется вместе с освобождением слота. Лимит остается ДО JSON-парсера.
Завершающий slash тоже защищен до router: корректный свободный запрос может получить
307 без генерации, а новый канонический POST обязан повторно пройти guard.

**Один процесс Uvicorn, один event loop, workers=1, без reload.** Проверка и захват
флага слота идут без await, поэтому не возникает гонки или очереди ожидающих:
второй авторизованный запрос сразу получает 429 без чтения тела/провайдера.
Слот удерживается от чтения тела до ответа и освобождается в finally при успехе,
ошибке и отмене. Отмена закрывает stream провайдера; общий клиент живет до shutdown.
Ограничение локальное, не распределенное: несколько workers/реплик не поддерживаются.

Router не дублирует верификацию/исправления и переводит прежние GenerationError
в HTTP-статусы (см. API). Неверная анкета — безопасный 422 без input; ошибки
авторизации DeepSeek — 503, не клиентский 401. План при ошибке отсутствует.
Существующие deadline и максимум три вызова сохранены; сетевых повторов нет.
Deadline сервиса начинается после приема/валидации анкеты, не ограничивает медленную
загрузку HTTP-тела. Этот локальный developer-сценарий не заменяет защиту публичного API.

Нет идемпотентности: повторный POST — новая потенциально платная генерация.
Disconnect не гарантирует отмену задачи Uvicorn или отсутствие расходов; обработчик
может закончить генерацию уже после отключения клиента. Нет серверного сохранения
меню у синхронного маршрута. Задания/PostgreSQL добавлены отдельно в MEAL-8 (ниже).
Redis и аккаунтов нет. Access token нельзя включать в Flutter.

## Точность денег

Чтение чисел JSON через `parse_float=Decimal`, внутренние суммы и умножения
только Decimal. Валюта — рубль; не хранить деньги в binary float.
В денежном JSON-сериализаторе Decimal преобразуется в число, максимум два
значимых десятичных разряда и предел 1 000 000 рублей позволяют проверить
обратное чтение в Decimal. Это преобразование транспортного формата,
не финансовая арифметика. Расчет использует локальный Decimal-контекст с
точностью 80 значащих цифр и ROUND_HALF_UP только для вывода до двух знаков.
Общий целый знаменатель порций сохраняется при агрегации КБЖУ и потребности:
периодические дроби не меняют границы округления и число упаковок.

## Каталог и оценка MEAL-4/MEAL-5

`Product.provenance` разделяет web-источники и явные synthetic_demo/synthetic_fixture.
Web-данные требуют официальную карточку сети, отдельные источники цены/КБЖУ
с AwareDatetime, канал/тип/условия цены и подтвержденную географию либо null.
Неясные цены, неподходящие единицы и неоднозначный съедобный выход не включаются
в активные граммовые записи. Наблюдаемая онлайн-цена `displayed` допускается
с `single_package_without_card=null` и пояснением условий: это не подтверждение
покупки без карты. Структурная валидация не доказывает истинность фактов;
требуется ручная сверка [CATALOG](CATALOG.md).
`catalog_version` обязателен в каталоге, расчете и результате генерации.
Неподтвержденный регион не заменяется пожеланием `GenerationRequest.price_region`.
Заявленный регион анкеты не подтверждает географию фактических цен.

Будущее разделение: **ингредиент → конкретный товар → предложение магазина**.
Ингредиент описывает кулинарную роль, товар — марку/состав/упаковку/КБЖУ,
предложение — цену, магазин, географию, условия и наличие. Пока все факты
привязаны к Product в JSON, PostgreSQL хранит только задания, не каталог.
Расширение единиц
и съедобного выхода — отдельная будущая задача, не неявный пересчет в ядре.

Все публичные Decimal-показатели сериализуются JSON-числами; строки числового
ввода провайдера допустимы, но не возвращаются наружу. Decimal остается внутри.
Float используется только на границе JSON, финансовая арифметика не менялась.
Вода разрешена в steps вне ingredients/корзины/КБЖУ; остальные пищевые добавки
должны быть ingredients с ID. Полное соответствие свободного текста не проверяется
автоматически: это обязательный пункт ручной оценки.

Сценарии оценки содержат отдельно request и ручной witness. Модели передается
только request через прежние CLI/endpoint, не свидетельство или готовый ответ.
По manifest ordinary (3 дня × 3 приема) и weekly (7 дней × 3 приема) готовы:
ручные witness проходят расчет по версии `5ka-2026-10-14-observed-v3` с допуском ±10%.
preferences, quick, tight-budget и impossible остаются blocked.
Качество реальной генерации еще не оценено; расчетная выполнимость witness
не доказывает качество или безопасность рецептов.
`evaluate_menu` не вызывает сеть: читает локальные RunSummary и использует
защищенный generated/ из прежнего CLI. Не дублирует генерационный сервис.
Опциональный --report старого CLI фиксирует исход/метаданные, не стоимость API.
В MEAL-6 CLI передает отдельный приемник `AttemptDiagnostic`, не общий атрибут
сервиса: нет смешивания истории между запросами. RunSummary.attempts сохраняет
стадию parsing/schema/calculation/constraints, коды, безопасные пути и числовые
actual/границы, полное число нарушений и флаг усечения. До 20 нарушений и 12 KiB
на попытку, до трех записей; старый report без истории читается с attempts=null.
Сохраняются причины и при успехе после исправления, и при исчерпании попыток.
Сырые ответы, неудачные меню, анкеты и произвольные msg/input/ctx не сохраняются;
extra-ключи в путях маскируются. HTTP-контракты не расширены, защитные лимиты сохранены.
Сбор диагностик — best effort, с узкой границей обработки Exception только вокруг
вспомогательного учета. Первый сбой отключает сборщик в текущем запуске;
резервный AttemptDiagnostic имеет available=false, violation_count/truncated=null,
без текста исключения. Сбой резервной записи тоже не влияет на основной результат;
неполная история не равна отсутствию нарушений. BaseException (в том числе отмена
и завершение процесса) не подавляется, deadline проверяется вне этой границы.
CLI печатает безопасную GenerationError до сохранения report. Если запись также
не удалась, отдельно сообщает файловый сбой и возвращает 2, не маскируя исходный код.
Локальный модуль evaluation проверяет явно выбранный --scenario: ID/ready,
подготовленную анкету, версию, witness расчетным ядром или минимальную цену
по каталогу. Не вызывает провайдер и не отправляет witness модели. Без --scenario
эта проверка не мешает обычной генерации; blocked не может получить success-сводку.
Пути output/report совместно проверяются без создания директорий и без resolve;
предотвращаются равенство, вложенность и уже существующие препятствия.
Внешние гонки не устранены, публикация каждого файла по-прежнему атомарна.

## Серверные задания и PostgreSQL MEAL-8

```text
POST /v1/generation-jobs → guard (Bearer, root_path, тело ≤64 KiB)
  → GenerationRequest → GenerationJobs.submit → JobStore / PostgreSQL → 202 queued
lifespan → один GenerationJobs worker → общий GenerationSlot
  → durable running → прежний MenuGenerationService → calculate_menu / полная проверка
  → durable completed + GenerationResult либо failed + безопасный код
GET /v1/generation-jobs/{id} → guard → JobStore → статус / проверенный результат
```

Router не обращается к PostgreSQL напрямую. `services/job_store.py` владеет
SQL/сериализацией/переходами; `services/generation_jobs.py` — очередью и worker;
`services/generation_slot.py` — общим слотом с прежним ASGI guard синхронного POST.
Захват без await атомарен только внутри одного event loop. Worker ожидает слот,
синхронный POST по-прежнему отказывает сразу с 429. Одновременно провайдера
использует не более одного цикла. Один общий HTTPX-клиент создается/закрывается
в lifespan, лимиты трех вызовов/deadline и transport retries=0 не изменены.

**Только один процесс, один worker генерации, без reload/реплик.** PostgreSQL —
durable-очередь, без Redis/Celery и отдельного брокера; это не мобильная SQLite.
Один драйвер psycopg 3 и AsyncConnectionPool: минимум 1, максимум 4 соединения
по умолчанию (конфигурируется 1–10), до 16 ожидающих, DB timeout 5 секунд по умолчанию
на ожидание/старт/statement/lock. Все SQL асинхронны и коротки; транзакции и
соединения освобождаются **до** провайдера. Пул может восстанавливать подключения,
но не повторяет генерацию. Сырые ошибки подключения и repr соединения не попадают
в сообщения фонового пула; DSN — SecretStr. Очередь до 4 queued по умолчанию
(конфигурируется 1–100), плюс один running. FIFO по created_at/id; снижение лимита
не удаляет принятые задания. BackgroundTasks HTTP-запроса не используются.

Базовая таблица PostgreSQL generation_jobs: id UUID, state TEXT с CHECK,
created_at/started_at/finished_at TIMESTAMPTZ, catalog_version TEXT,
request_json/result_json JSONB, безопасный error_code TEXT. CHECK ограничивает
комбинации состояния, времён, результата и ошибки. Decimal внутри JSONB — точные
строки без float; отдельных денежных столбцов нет. Если появятся — NUMERIC(scale 2).
В MEAL-9 добавлены установки и счётчики admission (ниже), но не профиль/таблицы меню/каталог.

### Транзакционные гарантии и процессные ограничения

- Admission: READ COMMITTED + общий transaction-scoped pg_advisory_xact_lock
  сериализуют count(queued) + INSERT. Параллельные POST через разные соединения
  не превышают предел; rollback освобождает lock без принятого задания.
- Процессный admission lock отдельно упорядочивает прием с остановкой worker.
  Cleanup выполняется до lock, затем доступность проверяется повторно. Lock охватывает
  весь create (ожидание пула, SQL, COMMIT), но не DeepSeek. Принятие — успешный COMMIT;
  начатый admission завершается перед переходом unavailable. POST, приостановленный
  на cleanup во время аварии, после возобновления получает 503 без INSERT. Ожидающие
  lock POST также проверяют актуальное состояние, одной начальной проверки нет.
  Уже принятый COMMIT не отменяется, даже если 202 еще не получен клиентом.
- Claim: один UPDATE с CTE SELECT FOR UPDATE SKIP LOCKED / RETURNING переводит
  выбранное queued в running. Два SQL-захвата не получают одну строку.
  Worker захватывает процессный слот до claim, но не соединение на время провайдера.
- Completed + result + finished_at сохраняются одной транзакцией/UPDATE.
  Failed не содержит результата; ошибки SQL откатываются без повторной генерации.
- Startup-recovery обновляет running/interrupted и mismatched queued в одной
  транзакции. Cleanup DELETE фильтрует terminal-состояния и finished_at.

Транзакция running фиксируется **до** обращения к провайдеру. После commit приема
задание не зависит от жизни HTTP-запроса; потеря 202 создает неопределенность
для клиента, а не разрешение безопасно повторять developer POST. App POST MEAL-9
имеет отдельные идемпотентность/квоты (ниже).
**Exactly-once внешнего платного вызова не обещается:** после ответа провайдера
возможна потеря БД/процесса до фиксации результата. Running не повторяется даже
если провайдер фактически еще не был вызван. Общий активный слот и startup-recovery
зависят от одного процесса; SQL-защита не означает поддержку нескольких workers:
второй процесс может ошибочно прервать чужое running при recovery.
Потеря соединения во время COMMIT может оставить неизвестный клиенту исход записи:
даже HTTP-ошибка не дает права автоматически повторять POST. На границе такого
сбоя приложение не пытается угадать исход и не выполняет повтор SQL/генерации.

На startup running атомарно превращаются в failed/interrupted: их нельзя
автоматически повторять из-за возможных затрат. Queued с другой версией каталога
становятся failed/catalog_version_mismatch; совпадающие подхватывает worker.
Версия повторно проверяется перед выполнением. Сохраненные completed можно
получить по исходной версии после обновления каталога. Обновление содержимого
каталога требует новой версии; равенство строки версии не является хешем содержимого.

Аварийный выход worker переводит его в unavailable под тем же admission lock.
Событие ERROR с фиксированным кодом `worker_unavailable` не содержит текста
исключения, traceback, SQL/DSN и данных задания. Worker не перезапускается автоматически.
После завершения SQL/проверки TTL GET заново проверяет доступность: queued/running
дают 503 `worker_unavailable`, completed/failed доступны, неизвестный ID дает 404,
если БД доступна. Строки queued/running не получают выдуманного terminal-состояния;
их обработает штатный startup-recovery. Недоступная БД дает отдельный безопасный
`job_storage_unavailable`, а не сырое SQL-исключение.

Штатный shutdown сначала под admission lock закрывает прием, затем освобождает lock
и отменяет/ожидает worker: его finally тоже нужен lock, поэтому ожидание не вложено
в критическую секцию. Штатная остановка не пишет аварийное событие. Отмена
закрывает stream, фиксирует interrupted для активного задания, оставляет queued,
затем закрывает HTTPX и пул. Дополнительный
interrupt_running после остановки покрывает отмену между COMMIT claim и получением
RETURNING; при недоступной БД переход завершит следующий startup. Ошибки сохранения
при отмене/shutdown дают отдельные фиксированные безопасные события
`worker_interruption_storage_unavailable` / `worker_shutdown_storage_unavailable`,
не подменяя исходную отмену. Сбой сохранения не вызывает повторной генерации.
Пропущенный terminal-переход будет interrupted при следующем запуске. Прочие неожиданные
ошибки цикла дают internal_error без деталей.

TTL по finished_at — 86400 секунд по умолчанию (конфигурируется, до 7 суток).
Удаляются terminal-строки целиком, не queued/running. Очистка при старте/между
работами, по интервалу простоя (60 секунд), а также при POST/GET; во время
провайдера фоновая очистка может задержаться, но GET не выдает просроченные данные.
После удаления 404 без tombstone. DELETE — логическое удаление; MVCC/VACUUM,
WAL и резервные копии не обещают немедленного физического стирания. TLS, права
ролей, шифрование носителя и retention резервных копий настраивает администратор.
Compose использует terse-ошибки без SQL/параметров/DETAIL строки; для внешней БД
нужна такая же политика, иначе серверные ошибки могут раскрыть содержимое JSONB.

## Серверная схема и миграции

Активна только **migrations/postgresql/**, первая независимая версия
001_generation_jobs_postgresql с явным пустым __depends__. Следующие миграции
должны явно ссылаться на предыдущие; примененные файлы не переписываются.
`python -m meal_budget.migrate_jobs apply|rollback` читает PostgreSQL URL из
GENERATION_JOBS_DATABASE_URL и использует sync backend yoyo postgresql+psycopg
того же psycopg 3. Credentials не передаются в argv/логи. API схему не создает;
включенный API без соединения/схемы безопасно прерывает startup, выключенный API
и ручной CLI PostgreSQL не открывают.

В migrations/archive_sqlite/ находится архивная SQLite-миграция. Доступного оригинала
для сравнения нет: ее исходное происхождение и побайтовая неизменность не подтверждены.
Это документированное ограничение; файл не реконструируется и не изменяется.
Его не читает рабочая команда и не включает Docker-образ. Старые SQLite-файлы не
читаются, не удаляются, данные не переносятся автоматически. Переход: остановить
старый API, сохранить файлы приватно, подготовить отдельную пустую PostgreSQL БД,
apply новой истории, заменить путь на URL, запустить один процесс. Старые ID не
присутствуют в новой БД (GET 404). Перенос — отдельная согласованная задача,
running нельзя молча воспроизводить. SQLite остается только будущему Flutter.

Rollback удаляет таблицу/индексы/данные, допустим лишь для тестовой/выведенной
БД. Проверяется на настоящем PostgreSQL: чистый apply, повторный apply,
rollback/reapply. Compose содержит PostgreSQL 17, healthcheck и volume postgres-data;
API опционален (profile api), миграции явные. Каталог остается JSON в образе.
Автономные тесты используют in-memory адаптер только из tests/, SQL-интеграция —
отдельные временные БД выделенного PostgreSQL. Нет fallback на SQLite и молчаливых
skips без БД. GitHub Actions имеет отдельный PostgreSQL service job.

## MEAL-9: установки и транзакционный app admission

```text
POST /v1/installations → bounded-body guard → random UUID + opaque token (256 bit)
  → installations: UUID / UNIQUE SHA-256(token) / created_at → 201 + no-store
POST /v1/app/generation-jobs → installation Bearer до тела → bounded body
  → GenerationRequest + Idempotency-Key → GenerationJobs.submit_app
  → тот же admission lock → JobStore.create_app → одна PostgreSQL-транзакция
  → прежняя очередь → прежний worker → прежний общий GenerationSlot → прежний сервис
GET /v1/app/generation-jobs/{id} → installation Bearer → SQL id + owner
  → TTL → worker availability → прежний JobStatus
```

Включение отдельно `GENERATION_APP_ENABLED=false` по умолчанию. Требует
`GENERATION_HTTP_ENABLED=true`, иначе create_app отказывает. Никаких второго worker,
слота/клиента или очереди нет. Developer API сохраняет отдельную авторизацию и
административное чтение временных заданий; его admission не тратит app-квоты.
Root_path/mounts/slash и fail-closed scope-proof общие, установка хранится только
в приватном scope до выхода middleware. Регистрация не требует Bearer, но тоже
требует guard и ограничение тела. Все app-ответы имеют no-store. Ключи/токены не
логируются и не передаются провайдеру, профиль остаётся на устройстве.

Новая yoyo 002 явно зависит от 001, не переписывает её. installations хранит
UUID, 32-byte SHA-256 token hash (UNIQUE + CHECK), created_at; секрет генерируется
`secrets.token_urlsafe(32)` с префиксом `mbi_`, не JWT. В задания добавлены nullable
installation_id FK, idempotency_key и request_hash: CHECK «все NULL либо все заполнены»,
формат ключа/длина хеша, UNIQUE(installation_id, idempotency_key). Ключ использует
COLLATE "C" для точного ASCII-сравнения независимо от default collation БД. Старые developer jobs
остаются с NULL без выдуманного владельца. Отдельной сырой копии анкеты нет.
SQL фильтрует владельца до преобразования JSONB в GenerationResult и до выдачи
ошибки состояния: чужие/неизвестные ID неотличимы (404), даже при аварии worker.

App admission держит тот же transaction-scoped QUEUE_LOCK, что developer create.
В READ COMMITTED после lock ищет и блокирует прежний job (FOR UPDATE), затем берёт
clock_timestamp() PostgreSQL/UTC для даты квоты и проверки TTL уже захваченной строки,
сравнивает SHA-256 канонизированных валидированных параметров. JSON sort/compact, явные defaults,
точное Decimal coefficient/exponent без float/округления, сортированные множества ID.
Версия каталога не входит в хеш; исходная версия задания не меняется при повторе.
Повтор возвращает только прежнее подтверждение 202, даже без доступного worker.
Конфликт — 409. Новый admission проверяет worker, общую очередь, global/personal quota,
увеличивает оба счётчика и вставляет job в одной транзакции. UNIQUE/FK/CHECK дополняют
DB-lock; защита не ограничивается процессным asyncio.Lock. Оба lock не удерживаются
во время провайдера. Процессный admission lock сохраняет упорядочивание MEAL-8 с
переходом worker в unavailable, включая POST, задержанный на cleanup.

app_daily_usage (UTC day PK, accepted > 0) и installation_daily_usage
(installation_id FK + UTC day PK, accepted > 0) независимы от TTL заданий.
Default 30 global и 3 personal — квота новых принятых заданий, не денежный бюджет.
Accepted COMMIT остаётся учтённым после failed/interrupted/restart/TTL. Rollback/отмена
до COMMIT не оставляют ни ключа/job, ни частичного счётчика. Старые дни удаляются
в транзакции следующего нового admission; повторы и отказы ничего не списывают.
Все установки делят global quota. 429 quotas получает Retry-After до UTC-полуночи,
полная очередь — 1 секунду без обещания освобождения.

Ключ хранится непосредственно в job: queued/running удерживают его, затем terminal
TTL (24 ч по умолчанию). Удаление строки атомарно удаляет ключ/анкету/результат,
нет dangling reference или вечного tombstone. После expiry тот же ключ — новый
admission с новой квотой/каталогом, GET старого ID — 404. Это не бессрочная гарантия.
COMMIT при обрыве соединения может быть неопределённым; тот же ключ позволяет
повторить подтверждение в пределах retention, но не восстановить истёкшие данные.

Регистрация использует отдельный advisory xact lock, count+INSERT ограничены
20/UTC-сутки и 200 всего по умолчанию. Установки не удаляются автоматически,
total-cap требует вмешательства оператора (Retry-After=86400 не гарантирует освобождение).
Токен бессрочный до удаления оператором/отключения API; recovery/rotation/revoke API нет.
Переустановка без сохранённого OS-secret создаёт новую установку, не возвращает старую.
Токен идентифицирует установку, **не уникального человека**; cap ограничивает таблицу,
но его можно исчерпать. Публичный запуск требует внешнего rate/connection/time limit,
контроля доступа пилота, HTTPS, redaction proxy/APM и дальнейшей abuse-политики.
Общий регистрационный секрет в Flutter не добавляется.

`migrate_jobs rollback --steps 1` на текущей истории откатывает только 002,
удаляет app jobs/установки/счётчики и сохраняет legacy developer jobs. Без --steps
rollback откатывает всю историю, как раньше. Миграции и API не запускаются вместе;
операции только на тестовой/выведенной БД, не как сброс квот. Schema-probe 002 нужен
только при включённом app API; выключенный app не ломает developer API со схемой 001.
Автоматических миграций нет. Все старые гарантии cancellation/recovery и внешнего
провайдера прежние: один процесс, до трёх вызовов, **не exactly-once**.
