# Подготовка оценки качества генерации

## Готовность

`examples/evaluation/scenarios.json` содержит шесть сценариев. В MEAL-5
**ordinary и weekly готовы (`ready`)** по версии `5ka-2026-10-14-observed-v3`:
ручные witness пересчитаны существующим ядром с допуском ±10% каждого показателя
каждого дня. ordinary 2026-10-15 завершился `attempts_exhausted`; после MEAL-6
запуск 2026-10-17 с `deepseek-flash`, thinking enabled / effort high дал проверенное
меню за три вызова (94,68 с). Первые два — `incomplete_response`, по 8192 completion
tokens; третий прошел проверки. `finish_reason` тогда не сохранялся: гипотеза об
упоре в лимит не подтверждена. Стабильность и weekly не доказаны. См. [STATUS](STATUS.md).

**MEAL-7: ordinary с 16384 выполнен пользователем — success за один вызов,
30,21 с, finish_reason=stop, 15 078 токенов.** Бюджет и КБЖУ прошли проверки;
подробности и ограничения — [STATUS](STATUS.md). weekly пока не запускался.
Проверки реализации автономные, через тестовый транспорт.

preferences, quick, tight-budget и impossible остаются **blocked**,
request/witness=null. Для них еще не подготовлены отдельные анкеты и свидетельства
(для impossible — проверенная нижняя граница), а не доказан дефицит всего каталога.
CLI отвергает их до провайдера даже с непустым импортом: calls=0.

Анкеты `ordinary.request.json`, `weekly.request.json` и планы
`ordinary.witness.json`, `weekly.witness.json` хранятся в отслеживаемом
`examples/evaluation/`; их содержимое совпадает с embedded request/witness manifest.
В generated/ сохраняются результаты провайдера и локальные отчеты.
Реальные персональные анкеты по-прежнему не коммитятся. Готовность означает лишь
расчетную выполнимость по **неподтвержденным наблюдениям**, не достоверность цен/КБЖУ.

Сценарии — технические синтетические примеры, не рекомендации по питанию.
Готовность отмечается только после ручной подготовки по конкретной версии каталога.

### Порции, шаги и время

Порции вручную проверены на обычные массы: 80–90 г сухого гарнира, 150 г филе,
200 г овощей; ужин содержит 70 г сухой чечевицы, хлеб и отдельный напиток.
Рецепты используют тушение/варку на воде, сливочное масло добавляется в готовое
блюдо. Нужны плита, две кастрюли/сковорода с крышкой, весы, холодильник;
параллельная готовка гарнира и филе/овощей. Это не замер в реальной кухне.
Заявлены 20/40/35/40/30 минут, лимит анкеты 45 минут **на рецепт**, не на весь день.
Тунец предварительно размораживается в холодильнике по упаковке: это время
**не входит** в 35 минут. Такие сценарии не заявляются quick или приготовлением
замороженного филе за 35 минут. Каждый повтор готовится заново; сроки хранения
готовых партий и безопасность термообработки сервер не удостоверяет.

Witness доказывает наличие одного математически допустимого решения, **не
готовый ответ для DeepSeek**. CLI отправляет только request, каталог и политику;
планы и их steps из manifest в сообщения модели не включаются.

## Подготовка одного сценария

Для пяти положительных сценариев вручную составить `GeneratedPlan`, проверить
порции и шаги, подсчитать каждый дневной показатель и покупки целых упаковок.
В manifest сохранить `request: GenerationRequest`, `witness: GeneratedPlan`,
`status=ready`, `catalog_version` использованного снимка. Свидетельство не является
эталоном качества или готовым ответом
для DeepSeek; оно доказывает лишь наличие одного допустимого решения.
До платного запуска вызвать `validate_plan(witness, request, catalog, tolerance)`:
ожидается расчет без нарушений, в том числе days/meals, исключений, времени,
бюджета и всех четырех показателей каждого дня. Не менять допуск ради успеха.

Бюджет ordinary/weekly/preferences/quick брать из корзины свидетельства с явно
описанным запасом; tight-budget — точно стоимость его целых упаковок.
Для impossible взять **непустой** доступный каталог после исключений, определить
минимальную цену одной допустимой упаковки и записать `minimum_purchase`.
Бюджет на 0.01 рубля меньше этой границы: любое меню с положительными граммами
требует минимум одну покупку с нуля. Нужна сверка границы по каталогу, одной
валидации схемы недостаточно. Для impossible эта подготовка пока не выполнена.

При явном --scenario CLI загружает manifest, отвергает неизвестный/blocked ID до
провайдера и проверяет все подготовленные данные. Анкета --request должна совпасть
с request сценария, версия выбранного каталога — с catalog_version. Положительный
witness проверяется validate_plan с текущим допуском; для impossible минимальная
цена после исключений должна совпасть с minimum_purchase. Сырые данные ошибок
не выводятся. Ошибка подготовки — код выхода 2, без вызовов и без success-report.
Это работает и с пустым, и с непустым каталогом. Без --scenario прежняя обычная
генерация поддерживается; она не объявляется запуском сценария оценки.

Ожидание положительных сценариев: `GenerationResult` либо безопасная ошибка
подбора, которая считается неудачей модели, **не доказательством невозможности**.
Невозможный сценарий должен завершиться безопасной ошибкой без непроверенного плана;
точный код может зависеть от ответа провайдера. Существующие лимиты — до 3 вызовов
и общий deadline, не новая реализация генерации.

## Ручные критерии

Для каждого результата оставить оценку «приемлемо / проблема / не проверено»
с коротким обоснованием, без личных данных:

| Поле сводки | Что проверить вручную |
| --- | --- |
| portions | Реалистичные массы одной порции и суммарный объем дня; dry/raw/cooked |
| recipe_clarity | Понятные шаги, последовательность, способ приготовления |
| unlisted_ingredients | Все пищевые добавки в ingredients: соль, масло, соусы, специи; обычная питьевая вода — исключение |
| variety_and_repeats | Разнообразие категорий и блюд, частота повторов по дням |
| cooking_convenience | Реальное удобство, оборудование, подготовка и заявленное время |
| package_leftovers | Закупка целых упаковок, использование и объем остатков |
| conclusion | Общий итог; проблемы безопасности/полноценности не считать проверенными сервером |

Сервер не доказывает полное соответствие свободного текста steps ингредиентам;
поиск слов или regex не дает такой гарантии. Ручная проверка рецептов обязательна.
Расчет подтверждает только математические ограничения, не качество питания.

## Автономная сводка — можно сейчас

```bash
uv run --frozen python -m meal_budget.evaluate_menu \
  --scenario ordinary --output evaluation/ordinary-summary.json
```

Без `--result` нет сети, ключей, загрузки `.env` и вызовов DeepSeek. Для ordinary/weekly
сводка имеет `outcome=not_run`, для остальных `blocked`; модель/режим/usage
неизвестны, ручная оценка пустая;
`metadata=null` означает, что запуск не выполнялся, а не нулевой расход платного запроса.
После запуска можно прочитать сохраненный report:

```bash
uv run --frozen python -m meal_budget.evaluate_menu --scenario ordinary \
  --result evaluation/ordinary-meal5-run-1.report.json --output evaluation/ordinary-summary-1.json
```

Указывается путь относительно `generated/`. В отчете сохраняется **версия запуска**,
а не подменяется новой версией рабочего каталога. Это сводка доверенного локального
report, не повторная независимая проверка меню и не сертификат готовности сценария.
Невалидный report, другой scenario, symlink, абсолютный путь и `..` отвергаются.
Попытка опубликовать outcome=success для blocked-сценария также отвергается.
Сводка без --result относится к отдельному `data/5ka-products.json`, не к demo.

## MEAL-7: один ordinary с лимитом 16384 — только после отдельного согласования

Пользователь выполнил один ordinary 2026-10-17: **success**, один вызов,
`finish_reason=stop`; безопасные метаданные отчета сверены в [STATUS](STATUS.md).
Это не доказывает влияние лимита 16384 на результат или стабильность генерации.
Следующая команда остается шаблоном нового отдельного ручного запуска,
**не разрешением на платный запрос или автоматический повтор**.
В старых отчетах нет finish_reason, восстановить его по числу токенов нельзя.

Готовая синтетическая анкета находится в `examples/evaluation/ordinary.request.json`
(без witness). Из корня репозитория; новый результат —
`generated/evaluation/ordinary-meal7-16384-run-1.menu.json`, отчет — соседний новый файл.
Не повторять команду автоматически; существующие файлы не заменяются.
Ключ вводить через скрытый ввод, не argv/history; CLI не читает `.env`:

```bash
set +x
read -r -s -p 'DeepSeek API key: ' DEEPSEEK_API_KEY
export DEEPSEEK_API_KEY
CATALOG_PATH=data/5ka-products.json DEEPSEEK_MODEL=deepseek-flash \
  DEEPSEEK_THINKING=enabled DEEPSEEK_REASONING_EFFORT=high \
  DEEPSEEK_MAX_OUTPUT_TOKENS=16384 GENERATION_TOTAL_TIMEOUT=180 \
  GENERATION_NUTRITION_TOLERANCE=0.10 \
  uv run --frozen --no-env-file python -m meal_budget.generate_menu \
  --request examples/evaluation/ordinary.request.json \
  --scenario ordinary --output evaluation/ordinary-meal7-16384-run-1.menu.json \
  --report evaluation/ordinary-meal7-16384-run-1.report.json
unset DEEPSEEK_API_KEY
```

`DEEPSEEK_MAX_OUTPUT_TOKENS` уже поддерживается Settings (1–32768) и передается как
`max_tokens` без преобразования. Default **8192** не изменен; 16384 применяется
только к этой команде. `deepseek-flash`, enabled/high заданы явно, не новые defaults.
Анкета, каталог `5ka-2026-10-14-observed-v3`, бюджет, цели и допуск ±10% прежние.
Общий deadline **180 с на весь цикл**, максимум **3 вызова**, без скрытых сетевых
повторов. Byte-limit по умолчанию остается 262144, read timeout — 60 с; увеличенный
лимит токенов не увеличивает их и не гарантирует завершения за deadline.

После запуска проверить `response_metadata` вместе с `attempts`, usage по каждой
попытке, calls/длительность и математические/ручные критерии. `stop` сам по себе
не означает приемлемое меню. Не оценивать эффект 16384 только по итоговому success:
важны причины всех отклоненных ответов. Report пока не хранит отдельные поля
reasoning_effort/max_tokens: параметры эксперимента зафиксированы этой командой.

### weekly — отдельный запуск после оценки ordinary

**Не выполнять оба блока подряд.** weekly пока не запускался и не запускается
автоматически: только отдельно после оценки ordinary и отдельного согласования.
Та же модель, enabled/high и 16384, прежние weekly-анкета, каталог и допуски;
другие новые файлы:

```bash
set +x
read -r -s -p 'DeepSeek API key: ' DEEPSEEK_API_KEY
export DEEPSEEK_API_KEY
CATALOG_PATH=data/5ka-products.json DEEPSEEK_MODEL=deepseek-flash \
  DEEPSEEK_THINKING=enabled DEEPSEEK_REASONING_EFFORT=high \
  DEEPSEEK_MAX_OUTPUT_TOKENS=16384 GENERATION_TOTAL_TIMEOUT=180 \
  GENERATION_NUTRITION_TOLERANCE=0.10 \
  uv run --frozen --no-env-file python -m meal_budget.generate_menu \
  --request examples/evaluation/weekly.request.json \
  --scenario weekly --output evaluation/weekly-meal7-16384-run-1.menu.json \
  --report evaluation/weekly-meal7-16384-run-1.report.json
unset DEEPSEEK_API_KEY
```

Одна команда может вызвать до трех платных запросов. Набор сценариев автоматически
не запускается. Стоимость API без подтвержденного тарифа не рассчитывается.
`--report` сохраняет успех или безопасный код ошибки, catalog_version,
запрошенную модель/режим, metadata с фактическими моделями, calls, длительностью и
предоставленным usage, результат бюджета/КБЖУ и шаблон ручной оценки.
С MEAL-6 локальный report также содержит `attempts`, описанный ниже.
С MEAL-7 отдельное `response_metadata` хранит безопасные причины завершения ответов.
При ошибке budget_pass/nutrition_pass остаются null: непроверенный план не сохраняется.
Локальные ошибки конфигурации/файла до старта сервиса не создают report.
До создания любых родителей CLI совместно проверяет output/report: запрещены
равенство и вложенность после лексической нормализации, существующие препятствия
и symlink. Безопасная нормализация не вызывает resolve и не следует ссылкам.
Проверка не устраняет внешние гонки между preflight и записью: атомарная публикация
продолжает защищать каждый файл отдельно.
Меню и report публикуются отдельно, не как атомарная пара; ошибка записи report
дает код 2, уже сохраненное меню может остаться. Файлы не перезаписываются без
`--overwrite`; все результаты внутри `generated/` с прежней Linux-защитой.
При сочетании GenerationError и OSError записи report код выхода также **2**
(локальная файловая ошибка); без сбоя записи ошибка генерации дает 1.
Исходный безопасный код/описание генерации выводятся в stderr **до записи report**,
независимо от ее исхода. Отдельная строка «Не удалось сохранить сводку ошибки.»
сообщает второй сбой, без текста OSError, traceback или секретов. Генерация не
повторяется, временный частичный файл удаляется прежним атомарным writer.

Для HTTP использовать прежний закрытый `POST /v1/menu-generations` и защиту
из README, заменив анкету на `examples/evaluation/ordinary.request.json`.
Сервер для реальной оценки запускать с CATALOG_PATH=data/5ka-products.json.
Endpoint не сохраняет меню и не создает CLI-report; HTTP результат/ошибку сохранять
в `generated/` защищенным способом, не выдавать их за формат --report.
Нового endpoint или второго сервиса генерации нет.

## MEAL-7: причины завершения в локальном отчете

Только `--report` получает отдельное `response_metadata`, максимум три записи:

```json
[
  {"attempt": 1, "finish_reason": "length"},
  {"attempt": 2, "finish_reason": "length"},
  {"attempt": 3, "finish_reason": "stop"}
]
```

Это **пример формата**, не результат нового платного прогона и не восстановление
причин исторического ordinary. Порядок соответствует полученным ответам в
`metadata.responses`; `attempt` — номер вызова, с которым сопоставляется `attempts`.
Сохраняются причины успеха, ошибок JSON/схемы/расчета/ограничений, а также ответов,
отвергнутых провайдером через `InvalidResponse`, без копирования меню или текста.
Сбой сборщика нарушений `attempts` не мешает отдельному учету причин завершения.

| Значение | Трактовка |
| --- | --- |
| `stop` | Провайдер завершил ответ; JSON, схема и ограничения еще должны пройти проверку |
| `length` | Провайдер сообщил об ограничении длины; даже валидный JSON не принимается |
| `content_filter`, `tool_calls`, `insufficient_system_resource` | Известная другая причина; меню не принимается |
| `other` | Любое неизвестное значение, включая произвольный текст или неожиданный тип; меню не принимается |
| null | Причина отсутствует/недоступна; завершенность не подтверждена, меню не принимается |

Набор фиксирован; исходный неизвестный текст не сохраняется. При `length` и прочих
неподтвержденных завершениях не разбирается меню, `previous_plan` для correction=null.
Исправления используют прежний общий бюджет вызовов. Схемы `GenerationResult`,
`GenerationMetadata`, `CallMetadata`, HTTP-ошибки/OpenAPI и файл успешного меню
**не расширены**: локальная диагностика отделена от публичных контрактов.

При parseable JSON-конверте с единственным choice причина сохраняется даже при
ошибке схемы message/model/usage. Обрезанный/невалидный JSON-конверт, несколько
choices, неподдерживаемое сжатие или превышение byte-limit не позволяют надежно
прочитать причину: null, без эвристического извлечения текста. HTTP-ошибки провайдера
не читаются; timeout/сетевая ошибка без ответа не создают запись. Поэтому calls
может быть больше числа записей. Если сломался сам вспомогательный приемник
response_metadata, история также может быть неполной, но исход генерации не меняется;
отмена и завершение процесса не подавляются. Отсутствие записи не означает `stop`.
Старые отчеты читаются с `response_metadata=null`, причины задним числом не известны.

`length` отличает ограничение длины от `stop`, но само по себе не различает
`max_tokens` и предел контекста и не объясняет распределение thinking/output tokens.
Ровно 8192 completion tokens без сохраненного finish_reason — лишь косвенный признак.
В report не сохраняются reasoning_content, сырой ответ, неудачные меню, пользовательский
текст или секреты. Математическая проверка не доказывает качество/безопасность питания.

## MEAL-6: контекст и диагностика без сети

`PromptProduct` — отдельное представление с семью полями: id, name, state,
state_basis, nutrition_per_100g, package_size_g, price. Числа/состояния/названия
сохраняются, исключаются только явно запрещенные request ID. Нет скрытого отбора
по цене или ассортименту. Provenance, URL, timestamps и legacy-поля остаются в
исходном каталоге и API без изменений; модель их по каждому SKU не получает.
Версия и однократный `catalog_context` сообщают demo_unverified, наблюдаемый характер
цен, неподтвержденную географию/условия и трактовку as_sold. Системные ограничения,
полная JSON Schema ответа и анкеты сохранены. Witness не отправляется.

### Размер исходных сообщений

Измерено на том же каталоге `5ka-2026-10-14-observed-v3`, обычном допуске 0.10 и

### Локальный формат attempts

Сбор включается только при `generate_menu --report`, через отдельный приемник
диагностики сервиса. `GenerationResult`, HTTP-ошибки и их metadata не расширены.
На каждой завершенной проверке сохраняются:

- `attempt`: номер 1–3;
- `stage`: parsing (JSON/конверт/пустой, обрезанный или слишком большой ответ),
  schema (GeneratedPlan), calculation (преобразование/ссылки ядра), constraints
  (ограничения, в том числе финальная успешная проверка);
- `available`: true при доступной диагностике; false при сбое ее сбора;
- `violations`: до 20 объектов с code, field, actual, minimum, maximum;
- `violation_count`: число нарушений **до** усечения; `truncated`: было ли усечение.

Пути используют только известные имена полей и индексы; корень обозначен `$`,
недоверенный extra-ключ — `*`, без исходного ключа. Неизвестный товар обозначается
`unknown_product_id` и путем до product_id, без копирования значения ссылки.
Числовые значения — Decimal-строки без округления, включая неокругленные КБЖУ;
для бюджета actual — стоимость целых упаковок, maximum — исходный бюджет.
Отсутствующая граница — null. Ограничение записи каждой попытки — 12 KiB UTF-8
с учетом отступов report; при превышении список сокращается дополнительно.
История содержит максимум три записи и помещается в прежний reader с лимитом 64 KiB.
Correction по-прежнему получает до 100 актуальных нарушений только последнего плана.

Пример **из синтетического теста**, не диагностика исторического ordinary:

```json
{
  "attempt": 1,
  "stage": "constraints",
  "available": true,
  "violations": [{
    "code": "nutrition_range",
    "field": "days.0.nutrition.protein_g",
    "actual": "5.0",
    "minimum": "9.000",
    "maximum": "11.000"
  }],
  "violation_count": 1,
  "truncated": false
}
```

После успешного исправления при исправном сборщике следующая запись имеет
available=true, stage=constraints,
violations=[], violation_count=0, truncated=false; первая остается в отчете.
При трех неудачах сохраняются все три причины и прежний безопасный error_code.
Сетевая ошибка/timeout без законченной проверки может дать calls больше числа
записей attempts; причины несостоявшегося ответа не выдумываются.
Старые отчеты совместимы: attempts=null означает, что история не собиралась.
В старой записи попытки без available подразумевается true.

### Сбой вспомогательной диагностики

Обычные исключения сборщика (включая ValueError/RuntimeError) изолированы только
вокруг вспомогательного учета. Проверка плана, провайдер, основной результат,
коды GenerationError и общий deadline этим обработчиком не охвачены.
После первого сбоя сломанный сборщик больше не вызывается в этой генерации;
последующие завершенные проверки получают независимый безопасный маркер:

```json
{"attempt":1,"stage":"constraints","available":false,"violations":[],"violation_count":null,"truncated":null}
```

Пустой список при available=false **не означает отсутствие нарушений**: счетчик и
усечение неизвестны. Не сохраняются ни текст/тип исключения, ни недоверенные данные.
Если невозможна даже резервная запись, сохраняется доступная часть истории;
неполная история не доказывает отсутствия нарушений. Метаданные calls и основной
проверенный результат/безопасная ошибка остаются независимыми от нее.
Состояние недоступности локально одному запуску, не сервису или следующему запросу.
CancelledError, KeyboardInterrupt и SystemExit проходят наружу; ошибки основной
валидации не подавляются. Дополнительных обращений провайдера или сброса deadline нет.

По умолчанию не сохраняются сырой ответ, меню неудачной попытки, анкета/wishes,
регион/свободный текст, ключи/заголовки, reasoning и msg/input/ctx ValidationError.
Проверенное меню по-прежнему сохраняется отдельно; хранить его надо как потенциально
личные данные. Защита файлов/endpoint, модель/thinking, анкеты/цели/допуски/бюджеты,
расчетное ядро, максимум три вызова и deadline не изменены. Оптимизатора нет.
