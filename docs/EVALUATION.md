# Подготовка оценки качества генерации

## Готовность

`examples/evaluation/scenarios.json` содержит шесть сценариев. В MEAL-5
**ordinary и weekly готовы (`ready`)** по версии `5ka-2026-10-14-observed-v3`:
ручные witness пересчитаны существующим ядром с допуском ±10% каждого показателя
каждого дня. **Платных прогонов MEAL-5 не было, качество ответов модели не оценено.**

preferences, quick, tight-budget и impossible остаются **blocked**,
request/witness=null. Для них еще не подготовлены отдельные анкеты и свидетельства
(для impossible — проверенная нижняя граница), а не доказан дефицит всего каталога.
CLI отвергает их до провайдера даже с непустым импортом: calls=0.

Анкеты `ordinary.request.json`, `weekly.request.json` и планы
`ordinary.witness.json`, `weekly.witness.json` хранятся в отслеживаемом
`examples/evaluation/`; их содержимое совпадает с embedded request/witness manifest.
В generated/ сохраняются только будущие результаты провайдера и локальные отчеты.
Реальные персональные анкеты по-прежнему не коммитятся. Готовность означает лишь
расчетную выполнимость по **неподтвержденным наблюдениям**, не достоверность цен/КБЖУ.

Сценарии — технические синтетические примеры, не рекомендации по питанию.
Готовность отмечается только после ручной подготовки по конкретной версии каталога.

## Контрольные планы ordinary и weekly

Все рецепты на одну порцию, каждый прием — ровно одна порция, без дробной подгонки.
18 различных SKU, 5 рецептов. Завтрак ежедневно: 80 г сухой овсянки, 150 г творога,
100 г вишни без косточки, 20 г миндаля. Ужин ежедневно: 70 г сухой чечевицы,
200 г рататуя, 40 г сметаны, 100 г хлеба, 250 г кефира (граммы, не мл).

разнообразного полноценного рациона. В каталоге мало свежих овощей/фруктов,

### Порции, шаги и время

Порции вручную проверены на обычные массы: 80–90 г сухого гарнира, 150 г филе,
200 г овощей; ужин содержит 70 г сухой чечевицы, хлеб и отдельный напиток.
Рецепты используют тушение/варку на воде, сливочное масло добавляется в готовое
блюдо. Нужны плита, две кастрюли/сковорода с крышкой, весы, холодильник;
параллельная готовка гарнира и филе/овощей. Это не замер в реальной кухне.
Заявлены 20/40/35/40/30 минут, лимит анкеты 45 минут **на рецепт**, не на весь день.
Тунец предварительно размораживается в холодильнике по упаковке: это время
**не входит** в 35 минут. Такие сценарии не заявляются quick или приготовлением
замороженного филе за 35 минут. Каждый повтор готовится заново; сроки хранения
готовых партий и безопасность термообработки сервер не удостоверяет.

Witness доказывает наличие одного математически допустимого решения, **не
готовый ответ для DeepSeek**. CLI отправляет только request, каталог и политику;
планы и их steps из manifest в сообщения модели не включаются.

## Подготовка одного сценария

Для пяти положительных сценариев вручную составить `GeneratedPlan`, проверить
порции и шаги, подсчитать каждый дневной показатель и покупки целых упаковок.
В manifest сохранить `request: GenerationRequest`, `witness: GeneratedPlan`,
`status=ready`, `catalog_version` использованного снимка. Свидетельство не является
эталоном качества или готовым ответом
для DeepSeek; оно доказывает лишь наличие одного допустимого решения.
До платного запуска вызвать `validate_plan(witness, request, catalog, tolerance)`:
ожидается расчет без нарушений, в том числе days/meals, исключений, времени,
бюджета и всех четырех показателей каждого дня. Не менять допуск ради успеха.

Бюджет ordinary/weekly/preferences/quick брать из корзины свидетельства с явно
описанным запасом; tight-budget — точно стоимость его целых упаковок.
Для impossible взять **непустой** доступный каталог после исключений, определить
минимальную цену одной допустимой упаковки и записать `minimum_purchase`.
Бюджет на 0.01 рубля меньше этой границы: любое меню с положительными граммами
требует минимум одну покупку с нуля. Нужна сверка границы по каталогу, одной
валидации схемы недостаточно. Для impossible эта подготовка пока не выполнена.

При явном --scenario CLI загружает manifest, отвергает неизвестный/blocked ID до
провайдера и проверяет все подготовленные данные. Анкета --request должна совпасть
с request сценария, версия выбранного каталога — с catalog_version. Положительный
witness проверяется validate_plan с текущим допуском; для impossible минимальная
цена после исключений должна совпасть с minimum_purchase. Сырые данные ошибок
не выводятся. Ошибка подготовки — код выхода 2, без вызовов и без success-report.
Это работает и с пустым, и с непустым каталогом. Без --scenario прежняя обычная
генерация поддерживается; она не объявляется запуском сценария оценки.

Ожидание положительных сценариев: `GenerationResult` либо безопасная ошибка
подбора, которая считается неудачей модели, **не доказательством невозможности**.
Невозможный сценарий должен завершиться безопасной ошибкой без непроверенного плана;
точный код может зависеть от ответа провайдера. Существующие лимиты — до 3 вызовов
и общий deadline, не новая реализация генерации.

## Ручные критерии

Для каждого результата оставить оценку «приемлемо / проблема / не проверено»
с коротким обоснованием, без личных данных:

| Поле сводки | Что проверить вручную |
| --- | --- |
| portions | Реалистичные массы одной порции и суммарный объем дня; dry/raw/cooked |
| recipe_clarity | Понятные шаги, последовательность, способ приготовления |
| unlisted_ingredients | Все пищевые добавки в ingredients: соль, масло, соусы, специи; обычная питьевая вода — исключение |
| variety_and_repeats | Разнообразие категорий и блюд, частота повторов по дням |
| cooking_convenience | Реальное удобство, оборудование, подготовка и заявленное время |
| package_leftovers | Закупка целых упаковок, использование и объем остатков |
| conclusion | Общий итог; проблемы безопасности/полноценности не считать проверенными сервером |

Сервер не доказывает полное соответствие свободного текста steps ингредиентам;
поиск слов или regex не дает такой гарантии. Ручная проверка рецептов обязательна.
Расчет подтверждает только математические ограничения, не качество питания.

## Автономная сводка — можно сейчас

```bash
uv run --frozen python -m meal_budget.evaluate_menu \
  --scenario ordinary --output evaluation/ordinary-summary.json
```

Без `--result` нет сети, ключей, загрузки `.env` и вызовов DeepSeek. Для ordinary/weekly
сводка имеет `outcome=not_run`, для остальных `blocked`; модель/режим/usage
неизвестны, ручная оценка пустая;
`metadata=null` означает, что запуск не выполнялся, а не нулевой расход платного запроса.
После запуска можно прочитать сохраненный report:

```bash
uv run --frozen python -m meal_budget.evaluate_menu --scenario ordinary \
  --result evaluation/ordinary-meal5-run-1.report.json --output evaluation/ordinary-summary-1.json
```

Указывается путь относительно `generated/`. В отчете сохраняется **версия запуска**,
а не подменяется новой версией рабочего каталога. Это сводка доверенного локального
report, не повторная независимая проверка меню и не сертификат готовности сценария.
Невалидный report, другой scenario, symlink, абсолютный путь и `..` отвергаются.
Попытка опубликовать outcome=success для blocked-сценария также отвергается.
Сводка без --result относится к отдельному `data/5ka-products.json`, не к demo.

## Один будущий платный запуск ordinary — не выполнен

Готовая синтетическая анкета находится в `examples/evaluation/ordinary.request.json`
(без witness). Из корня репозитория; новый результат —
`generated/evaluation/ordinary-meal5-run-1.menu.json`, отчет — соседний новый файл.
Не повторять команду автоматически; существующие файлы не заменяются.
Ключ вводить через скрытый ввод, не argv/history; CLI не читает `.env`:

```bash
set +x
read -r -s -p 'DeepSeek API key: ' DEEPSEEK_API_KEY
export DEEPSEEK_API_KEY
export DEEPSEEK_MODEL=deepseek-flash
export DEEPSEEK_THINKING=disabled
CATALOG_PATH=data/5ka-products.json GENERATION_NUTRITION_TOLERANCE=0.10 \
  uv run --frozen python -m meal_budget.generate_menu \
  --request examples/evaluation/ordinary.request.json \
  --scenario ordinary --output evaluation/ordinary-meal5-run-1.menu.json \
  --report evaluation/ordinary-meal5-run-1.report.json
unset DEEPSEEK_API_KEY
```

Одна команда может вызвать до трех платных запросов. Набор сценариев автоматически
не запускается. Стоимость API без подтвержденного тарифа не рассчитывается.
`--report` сохраняет успех или безопасный код ошибки, catalog_version,
запрошенную модель/режим, metadata с фактическими моделями, calls, длительностью и
предоставленным usage, результат бюджета/КБЖУ и шаблон ручной оценки.
При ошибке budget_pass/nutrition_pass остаются null: непроверенный план не сохраняется.
Локальные ошибки конфигурации/файла до старта сервиса не создают report.
До создания любых родителей CLI совместно проверяет output/report: запрещены
равенство и вложенность после лексической нормализации, существующие препятствия
и symlink. Безопасная нормализация не вызывает resolve и не следует ссылкам.
Проверка не устраняет внешние гонки между preflight и записью: атомарная публикация
продолжает защищать каждый файл отдельно.
Меню и report публикуются отдельно, не как атомарная пара; ошибка записи report
дает код 2, уже сохраненное меню может остаться. Файлы не перезаписываются без
`--overwrite`; все результаты внутри `generated/` с прежней Linux-защитой.

Для HTTP использовать прежний закрытый `POST /v1/menu-generations` и защиту
из README, заменив анкету на `examples/evaluation/ordinary.request.json`.
Сервер для реальной оценки запускать с CATALOG_PATH=data/5ka-products.json.
Endpoint не сохраняет меню и не создает CLI-report; HTTP результат/ошибку сохранять
в `generated/` защищенным способом, не выдавать их за формат --report.
Нового endpoint или второго сервиса генерации нет.
