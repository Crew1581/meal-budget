# API

## Реализованные маршруты

### GET /health

`200`: `{"status": "ok"}`. Проверяет только процесс, без БД/DeepSeek.

### GET /v1/products

`200`: объект с `catalog_version`, `data_status: "demo_unverified"`, `warning`
и `products`. Нет фильтров и пагинации. По умолчанию выбран demo-каталог
`data/products.json` (`demo-meal-3-v1`), три synthetic_demo-продукта и явное
demo_unverified-предупреждение. Реальный снимок выбирается явно:
`CATALOG_PATH=data/5ka-products.json`. Ниже его текущий ответ при заблокированном сборе:

```json
{
  "catalog_version": "5ka-2026-10-13-blocked-v1",
  "data_status": "demo_unverified",
  "warning": "Сбор карточек 5ka.ru заблокирован HTTP 403: проверенных товаров нет. Регион, магазин, цены и наличие не подтверждены. Будущий снимок онлайн-доставки не гарантирует цену или наличие в конкретном офлайн-магазине.",
  "products": []
}
```

Состояния: `dry`, `raw`, `cooked`. КБЖУ относятся к указанному состоянию
и 100 г, размер упаковки — граммы. КБЖУ конкретного товара и все количества — числа.
Деньги — JSON-числа в рублях, не строки и не копейки; `89.9` равно `89.90`.
`Product.provenance` расширяет прежние общие метаданные. `price_source`,
`price_region`, `price_updated_at` сохранены как deprecated поля совместимости,
производные от источника цены: URL, подтвержденный регион либо null и дата
из timestamp. У synthetic demo/fixture регион и дата null, источник — явная note.
Эти общие поля не заменяют provenance, противоречия между ними отклоняются.
Для web-записи обязательны:

- `kind=web`, `chain=Пятёрочка`, `product_url` — официальная карточка 5ka.ru;
- `retailer_product_id` — опубликованный ID либо null, не выдумывается;
- `nutrition`: отдельные `url` сети/официального производителя и `checked_at`;
- `price`: URL той же карточки и `checked_at` — timestamps ISO с часовым поясом;
- `channel=online_delivery|offline_store`, `region_confirmed`, `region`, `store`;
  неподтвержденные region/store — null, не «Москва» из пожелания пользователя;
  подтвержденный регион может не иметь выбранного магазина, офлайн-цена требует магазин;
- `price_type=regular|promotional`; unclear отклоняется в активном каталоге;
- `single_package_without_card=true`, `conditions` либо null, `valid_from`/`valid_until`
  — опубликованные даты акции YYYY-MM-DD либо null. Для акции условия обязательны.

Все записи в активном каталоге требуют корректной фиксированной массы в граммах.
Схема не проверяет истинность страницы или полноту условий акции: обязательна
ручная проверка [CATALOG](CATALOG.md). `synthetic_fixture` — только явно помеченные
автономные тестовые данные с note; synthetic_demo — демонстрационные данные обычного
запуска. Оба типа не данные сети. Старые demo-ID не переиспользованы.
Реальный снимок пуст после HTTP 403; отсутствие товаров не нарушает startup.
Автоматического fallback на другой каталог нет.

### POST /v1/menu-calculations

Детерминированный расчет присланного меню, **не генерация и не рекомендация
по питанию**. Каталог уже загружен приложением. Клиент не передает цены и КБЖУ.

Исторический синтетический запрос (также `examples/menu-calculation.json`):
работает по умолчанию с demo-каталогом и отдельно с тестовой fixture; в пустом реальном снимке
дает 422 `unknown_product_id`. Это не реальная корзина «Пятёрочки».

```json
{
  "recipes": [
    {
      "id": "oats-demo",
      "name": "Технический пример овсяных хлопьев",
      "servings": 2,
      "ingredients": [{"product_id": "oats", "grams": 100}]
    }
  ],
  "days": [{"day": 1, "meals": [{"recipe_id": "oats-demo", "servings": 1}]}],
  "budget": 100
}
```

Контракт и технические пределы (не медицинские нормы):

- `recipes`: 1–100 рецептов с уникальным `id`; каждый должен использоваться.
  `id` и ссылки — 1–64 символа `a-z`, `0-9`, `_`, `-`; `name` — 1–120 символов.
- `recipe.servings`: строго целое 1–100. `ingredients`: 1–100 элементов,
  без повторного `product_id` в одном рецепте.
- `ingredient.grams`: положительный конечный Decimal до 100 000 г,
  не более 12 значащих десятичных цифр и 6 знаков после запятой.
  Граммовки относятся **ко всему рецепту**, не к одной порции.
- `days`: 1–31 день, `day` — строго целое 1–31; список идет от 1 по порядку
  без пропусков и повторов. `meals`: 1–10 приемов пищи в день.
- `meal.servings`: положительный конечный Decimal до 100, не более 9
  значащих десятичных цифр и 6 знаков после запятой. Это количество съедаемых
  порций рецепта; допустимы дробные порции и повторное использование рецепта.
  Это не учет приготовленной партии: сумма порций может превышать выход рецепта.
- `budget`: существующий денежный тип — положительный конечный Decimal до
  1 000 000 рублей, максимум два знака после запятой, бюджет **всего периода**.
- Все ссылки должны существовать. Неизвестные поля, пустые списки, нулевые,
  отрицательные, NaN и бесконечные значения запрещены. Decimal принимает JSON-числа
  и десятичные строки; строго целые поля не принимают строки, bool и дроби.

Расчет:

1. КБЖУ рецепта — сумма `grams / 100 × nutrition_per_100g` ингредиентов.
   КБЖУ приема — КБЖУ рецепта × `meal.servings / recipe.servings`.
2. Потребность — сумма `ingredient.grams × meal.servings / recipe.servings`
   по **всем** использованиям всех рецептов за период.
3. Только после агрегации: `packages = ceil(required_grams / package_size_g)`;
   `purchased_grams = packages × package_size_g`,
   `remaining_grams = purchased_grams - required_grams`, `cost = packages × price`.
4. Все продукты покупаются с нуля, в том числе масло и специи. Остаток —
   неиспользованный купленный продукт, не готовое блюдо. Запасы, сроки хранения
   и готовые остатки не учитываются. Масса соответствует dry/raw/cooked каталога,
   без неявного пересчета; шагов приготовления и веса готового блюда нет.
5. Внутри — Decimal, локальная точность 80 значащих цифр. При агрегации
   сохраняется общий целый знаменатель порций, чтобы периодические дроби не
   изменяли границы упаковок и округления. Промежуточные значения не округляются
   до сотых; вывод показателей — два знака, ROUND_HALF_UP. `meal.servings`
   возвращается без потери принятой точности. Сумма округленных приемов может
   отличаться от округленного итога дня: итоги считаются независимо до округления.
6. `within_budget` сравнивает точную стоимость с бюджетом до округления вывода.
   Превышение — нормальный `200`, меню не меняется. `budget_remaining` может
   быть отрицательным; `over_budget_by = max(total_cost - budget, 0)`.

Пример результата `200` **только для synthetic fixture** и запроса выше:

```json
{
  "catalog_version": "synthetic-meal-3-v1",
  "data_status": "demo_unverified",
  "warning": "Синтетические fixtures MEAL-3, не реальные товары и не проверенные цены или КБЖУ.",
  "days": [
    {
      "day": 1,
      "meals": [
        {
          "recipe_id": "oats-demo",
          "servings": 1,
          "nutrition": {"calories_kcal": 185, "protein_g": 6.5, "fat_g": 3.5, "carbs_g": 31}
        }
      ],
      "nutrition": {"calories_kcal": 185, "protein_g": 6.5, "fat_g": 3.5, "carbs_g": 31}
    }
  ],
  "nutrition": {"calories_kcal": 185, "protein_g": 6.5, "fat_g": 3.5, "carbs_g": 31},
  "shopping_list": [
    {
      "product_id": "oats",
      "name": "Овсяные хлопья",
      "required_grams": 50,
      "package_size_g": 500,
      "packages": 1,
      "purchased_grams": 500,
      "remaining_grams": 450,
      "price": 89.9,
      "cost": 89.9
    }
  ],
  "budget": 100,
  "total_cost": 89.9,
  "within_budget": true,
  "budget_remaining": 10.1,
  "over_budget_by": 0
}
```

Список покупок отсортирован по `product_id`; порядок рецептов и ингредиентов
не влияет на результат. Все числовые показатели — JSON-числа, не строки.
JSON не обязан сохранять конечные нули (`89.9` равно `89.90`).
`catalog_version` совпадает с версией загруженного каталога; исторические demo-ID
сохранены в demo-каталоге с прежними значениями, не заменены новыми упаковками молча.

Ошибки меню — `422`, без traceback, тела запроса и внутренних деталей:

```json
{
  "detail": [
    {
      "code": "unknown_product_id",
      "field": "recipes.0.ingredients.0.product_id",
      "message": "Неизвестный product_id: missing"
    }
  ]
}
```

`code` стабилен, описание предназначено для человека (стандартные сообщения
валидации Pydantic могут быть на английском). Коды доменных ошибок:
`unknown_product_id`, `unknown_recipe_id`, `unused_recipe`, `duplicate_recipe_id`,
`duplicate_product_id`, `invalid_day_sequence`. Стандартные ошибки полей
используют Pydantic-коды, например `missing`, `too_short`, `too_long`,
`greater_than`, `less_than_equal`, `finite_number`, `int_type`,
`decimal_max_places`, `extra_forbidden`, `json_invalid`.
`field` — путь с нулевыми индексами; при валидации начинается с `body`,
при ошибке всего меню — `body`; при повторе ингредиента — путь рецепта,
описание содержит проблемный ID. Ошибки ссылок ядра имеют точный путь без `body`.

### Стандартная документация

`GET /docs`, `GET /redoc`, `GET /openapi.json`. OpenAPI описывает только
работающие маршруты; генерация и Bearer security scheme присутствуют только
при `GENERATION_HTTP_ENABLED=true`.

## POST /v1/menu-generations — закрытый endpoint MEAL-3

Python-схема: `meal_budget.schemas.generation.GenerationRequest`.
Синхронный по HTTP сценарий: POST ожидает завершения асинхронного сервиса,
`200` содержит `GenerationResult`, не ID задания. Сервис и CLI переиспользуются.
По умолчанию endpoint выключен: 404, отсутствует в OpenAPI, платных вызовов нет.
Включение требует `GENERATION_HTTP_ENABLED=true` и непустого
`GENERATION_ACCESS_TOKEN` (печатный ASCII без пробелов); иначе ошибка конфигурации.

Доступ разработчика: `Authorization: Bearer <GENERATION_ACCESS_TOKEN>`, отдельный
от ключа DeepSeek секрет сервера, **не токен будущего Flutter-клиента**.
Сравнение через `secrets.compare_digest`, до чтения тела/JSON и вызова провайдера;
заголовок и токен не логируются. OpenAPI содержит HTTP Bearer-аутентификацию.
Только один процесс Uvicorn (`--workers 1`, без reload); один слот на весь запрос,
без очереди, занятый слот дает немедленный 429 до чтения тела/провайдера.
Тело не более **65536 байт** до JSON-разбора: проверяется Content-Length и
фактически прочитанные чанки, в том числе без длины и с chunked encoding.

ASGI `root_path` (например `/api` или вложенный `/gateway/api`) учитывается тем же
`get_route_path(scope)`, что в маршрутизации Starlette/FastAPI. Guard не пропускает
защиту по полному URL. Endpoint дополнительно требует серверное подтверждение
проверок, привязанное к текущему scope; без него — 401 без генерации даже с верным
токеном. Подтверждение не берется из заголовков/JSON и не переносится между запросами.
Запрос с завершающим `/` тоже проходит guard: 401/413/429 имеют приоритет над
307 на канонический путь. Редирект не вызывает провайдера; новый POST проверяется заново.
Внешний proxy с `--root-path /api` передает upstream путь без `/api`; Uvicorn сам
добавляет префикс в ASGI scope и Location, а не удаляет его из HTTP request target.

Нет идемпотентности, сохранения меню, заданий и автоматических повторов.
Каждый повторный POST может снова стоить денег: до трех вызовов DeepSeek.
Отключение клиента/timeout не доказывает отсутствия расходов. При отмене задачи
поток закрывается и слот освобождается; при disconnect обработка может продолжаться
до результата или существующего общего deadline. Инструкции запуска и curl — в README.

Ниже исторический пример формы, **не проверенный реальный сценарий MEAL-4**.
Для автономного технического теста используются `examples/generation-request.json`
и synthetic fixture; шесть будущих сценариев пока blocked (см. [EVALUATION](EVALUATION.md)).

```json
{
  "days": 7,
  "budget": 2500.50,
  "daily_targets": {
    "calories_kcal": 2000, "protein_g": 100, "fat_g": 70, "carbs_g": 250
  },
   "excluded_product_ids": [],
  "disliked_product_ids": [],
  "max_cooking_minutes": 30,
  "meals_per_day": 3,
  "price_region": "Москва",
  "wishes": "Простые блюда"
}
```

- `days`: строго целое 1–31, по умолчанию 7.
- `budget`: положительный конечный Decimal до 1 000 000 рублей на **весь период**,
  максимум два значимых разряда после запятой; принимаются числа и десятичные строки.
- `daily_targets`: ежедневные КБЖУ, каждое поле положительное и конечное,
  максимум 100 000. Это технический предел, не медицинская норма.
- Списки ID: до 500 элементов каждый, по умолчанию пустые. ID длиной 1–64,
  символы `a-z`, `0-9`, `_`, `-`. Сервис проверяет существование ID до вызова провайдера.
- `max_cooking_minutes`: строго целое 1–240, предел **заявленного** времени блюда.
- `meals_per_day`: строго целое 1–10.
- `price_region`: непустая строка до 120 символов.
  Это пожелание пользователя, не подтверждение географии источника; цены
  не переименовываются в московские. Неподтвержденная география остается в provenance.
- `wishes`: до 2000 символов, по умолчанию пустая строка.

Неизвестные поля запрещены. Строки очищаются от пробелов по краям.
Булевы значения не принимаются вместо строго целых полей.
Фиктивного или непроверенного меню в успешном HTTP-ответе нет.

### Структура ответа модели и результата сервиса

`GeneratedPlan` содержит только `recipes` и `days`, без бюджета и рассчитанных итогов.
Все пределы `Recipe`, `Ingredient`, `MenuDay`, `Meal` из расчетного контракта
сохраняются: 1–100 рецептов, 1–100 ингредиентов в рецепте, 1–31 день,
1–10 meals, положительные граммовки и порции, название до 120 символов.
`GeneratedRecipe` дополнительно требует:

- `steps`: 1–20 непустых шагов, каждый до 500 символов;
- `cooking_minutes`: строго целое 1–240 и не выше `max_cooking_minutes` анкеты.

Сервис преобразует план в `MenuCalculationRequest` с бюджетом из исходной анкеты;
ядро проверяет ссылки, уникальность и последовательность, считает целые упаковки.
Дополнительно обязательны точное число дней и meals, отсутствие исключенных
продуктов и попадание каждого дневного показателя в включительный диапазон
`target × (1 ± GENERATION_NUTRITION_TOLERANCE)` по неокругленным данным.
По умолчанию ±10%, продуктовая настройка, не медицинская норма.
Повторы разрешены; нелюбимые продукты не вызывают отказа, только предупреждение.

`GenerationResult` (Python/CLI и HTTP `200`) содержит:

- `plan`: проверенный `GeneratedPlan`, включая инструкции и заявленное время;
- `catalog_version`: версия использованного каталога, также в calculation;
- `calculation`: прежний `MenuCalculationResponse`, с demo-маркировкой и предупреждением;
- `warnings`: предупреждение каталога и используемые нелюбимые ID, если есть;
- `nutrition_tolerance`: использованный относительный допуск (JSON-число);
- `metadata`: `calls`, `duration_seconds`, `responses` (по полученному ответу):
  `model` и `usage` либо `null`. Usage включает предоставленные prompt/completion/total
  и cache-hit/cache-miss tokens; не содержит произвольных полей провайдера.

В `plan` grams и servings — JSON-числа, как и КБЖУ/деньги в calculation.
В MEAL-4 это намеренное изменение прежней сериализации Decimal-строк;
числовые строки от провайдера по-прежнему могут приниматься на входе.
Decimal остается внутри всех вычислений, float — только граница JSON.
OpenAPI serialization-схемы описывают числовой выход.
Сырые ответы, reasoning_content и тела ошибок провайдера не возвращаются.

Обычная питьевая вода разрешена в steps вне ingredients/корзины/КБЖУ.
Все остальные пищевые ингредиенты должны быть в ingredients с product_id каталога.
Это правило промпта и ручной проверки: автоматическое полное сопоставление
свободного текста шагов с ingredients не обещается, regex-гарантии нет.

`GenerationError` имеет безопасное описание, `code` и `metadata`; непроверенного
плана в ошибке нет. Коды: `configuration_missing`, `invalid_request`,
`provider_unavailable`, `provider_authorization` (401/403), `provider_rate_limit` (429),
`provider_timeout`, `generation_timeout`, `invalid_response`, `attempts_exhausted`.
402/400/422 и прочие non-200 относятся к `provider_unavailable`, без сырого тела.
Стабильный HTTP-контракт ошибки (без input, traceback или непроверенного меню):

```json
{"detail":{"code":"generation_busy","message":"Генерация уже выполняется.","metadata":null}}
```

`metadata` содержит прежние `calls`, `duration_seconds`, `responses`, если сервис
начал обработку; для доступа, размера тела и схемы — `null`.

| HTTP | code | Причина |
| --- | --- | --- |
| 401 | `unauthorized` | Нет/неверный Bearer либо нет серверного подтверждения guard; `WWW-Authenticate: Bearer` |
| 413 | `request_too_large` | Превышение лимита тела; JSON еще не разобран |
| 422 | `invalid_request` | Неверная схема/JSON анкеты либо неизвестные ID предпочтений |
| 429 | `generation_busy` | Локальный слот занят, нового вызова провайдера нет |
| 422 | `attempts_exhausted` | За три попытки не получен план, прошедший ограничения |
| 504 | `provider_timeout`, `generation_timeout` | Сетевой timeout или общий deadline |
| 503 | `provider_unavailable`, `provider_rate_limit` | Сеть/недоступность/лимит провайдера |
| 503 | `provider_authorization` | DeepSeek 401/403 — не ошибка авторизации клиента |
| 503 | `configuration_missing` | Не настроены корректные ключ/модель/URL провайдера |
| 503 | `catalog_unavailable` | Активный каталог пуст; calls=0, провайдер не вызывается |
| 502 | `invalid_response` | После исправлений последний ответ невалиден по JSON/схеме/transport |

Авторизация проверяется раньше занятости и тела: неавторизованный запрос всегда
получает 401, не 429/413/422. Некорректная анкета в свободном слоте — 422 без вызова
провайдера. Сетевые/HTTP-ошибки провайдера завершают цикл сразу без повторов.

Не более 3 вызовов: исходный + 2 исправления. Невалидный/обрезанный ответ
тратит попытку, а не считается успешным. Исчерпание попыток возвращает
«Не удалось подобрать меню с указанными условиями»; код последней проблемы
различает невалидный ответ и не прошедший ограничения план. Сетевые и HTTP-ошибки
не повторяются. Метаданные могут быть неполными при timeout или неразобранном ответе;
количество начатых вызовов известно, фактический расход токенов — не обязательно.
Сервис не проверяет безопасность инструкций, реальное время и медицинскую полноценность.
