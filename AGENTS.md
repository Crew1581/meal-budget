# Правила разработки

Общаться и писать документацию на русском. До изменения читать существующий
код, тесты, Git status/diff, [README](README.md) и [STATUS](docs/STATUS.md).
После задачи обновлять STATUS по фактически выполненной работе: это актуальный
снимок, не журнал. Долгосрочные задачи вести в ROADMAP, архитектурные решения —
в DECISIONS. Не записывать секреты, личные данные и полные логи. Не заявлять
о проверках, которые не запускались. Не перезаписывать чужие
изменения, не выполнять повторный git init, не делать commit без запроса и push.
Не читать и не выводить .env, ключи, дампы и пользовательские данные.

## Архитектурные ограничения

- Небольшой FastAPI-проект, не микросервисы. Pydantic v2; сборка в `create_app()`,
  ресурсами владеет lifespan. Router отвечает за HTTP, схемы за контракт.
- Service добавлять с реальной логикой, не создавать пустые репозитории/интерфейсы.
- Flutter и локальная SQLite хранят настройки, меню и заметки без аккаунтов.
  Сервер в будущем хранит каталог и временные задания, не пользовательский профиль.
- Деньги — Decimal в рублях, не binary float; максимум два знака после запятой.
  float разрешён только на границе сериализации денежного JSON-числа.
  Если появится PostgreSQL, денежные поля — NUMERIC с scale 2.
- PostgreSQL сейчас не требуется. DeepSeek пока не вызывается, ключ только
  на сервере, не логировать секреты, настройки целиком и тела с чувствительными данными.
- Не выдавать запланированное за реализованное. Не добавлять неиспользуемые зависимости.
- Изменение поведения/контракта сопровождается тестами и документацией.
  Установка только через uv, версии из uv.lock; не смешивать с pip.

## Проверки

```bash
uv sync --frozen
uv run --frozen ruff check .
uv run --frozen ruff format --check .
uv run --frozen pytest
```

Сначала узкие тесты, затем связанные и полный набор; внешняя сеть и ключ
DeepSeek не нужны. После правок проверить diff. Не ослаблять валидные тесты.
Не заявлять об успешной проверке без запуска. Для изменений контейнера:
`docker build -t meal-budget:local .` и проверка маршрутов в контейнере.

## Будущие серверные миграции

При появлении серверной БД использовать **yoyo-migrations**, не Alembic:
каждое изменение схемы — новая версионируемая миграция с явными зависимостями
и порядком. Применённые миграции не переписывать. Где возможно, предусмотреть
корректный rollback и проверить его. Документировать реальные команды применения
и отката вместе с подключением БД. Credentials передавать через окружение,
не аргументы с паролями, не печатать DSN. Проверять применение к чистой тестовой
БД. Миграции не запускать автоматически при старте API.
Сейчас не создавать фиктивные миграции и не устанавливать yoyo.
Миграции SQLite в Flutter — отдельная задача клиента, не серверные yoyo-миграции.
